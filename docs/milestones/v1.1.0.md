# v1.1.0 — Notification Forwarding Experience

## Goal

Make NotiRelay read like a small Windows 11 utility instead of an operational
dashboard: a stable custom `[icon] NotiRelay` title bar, a Task Manager-style
navigation Shell, Settings-style pages, plain user-facing language, and a positive
Notification forwarding switch.

## Accepted UX Direction

- Keep `Relay`, `Delivery`, and `Outbox` as internal domain concepts; use
  **Notification forwarding**, **App**, **Destination**, **Rule**, and **Send** in
  the interface.
- Use the short navigation labels Home, Apps, Destinations, Rules, Activity, and
  Settings; page headings may be more descriptive.
- Use the standard 32 px Windows title-bar height with the vector application mark,
  application name, and primary title text. Preserve native caption buttons, drag,
  double-click, and system-menu behavior, and keep the title bar visually open without
  a bottom divider.
- Keep navigation entirely below the title bar. The user alone controls whether the
  side-by-side NavigationView is a 232 px expanded pane or a 48 px compact icon rail;
  window width never changes that choice and no overlay pane is used. Put an icon-only
  pane command at the top of the menu, following Task Manager's title-bar/navigation
  separation.
- Persist the user's pane choice and default to expanded on first launch. Compact
  navigation items expose localized tooltips, while each page remains the source of
  its full title and subtitle.
- Keep the native NavigationView item template and selection treatment so compact
  icons remain centered and expanded icons share the standard text baseline. Keep
  page navigation at the top and Forwarding status plus Settings at the bottom.
- Implement the pane command as a non-selecting `NavigationViewItem` so its hit-test
  area, PointerOver background, icon column, and keyboard behavior are identical to
  the other navigation rows. Keep the visible command icon-only and expose its current
  expand/collapse action through localized tooltips and automation properties.
- Use left-aligned responsive content containers instead of page-local accidental
  centering.
- Keep the accepted Task Manager-style Shell, but use Windows Settings interaction
  grammar inside pages: independently bounded setting rows, whole-row navigation,
  right-side accessories, chevrons only for detail navigation, and responsive
  accessory reflow. Use a shared presentation-only `SettingsRow` for this grammar.
- Use a 232 px expanded pane and 48 px compact pane. Window width never changes the
  persisted user choice.
- Use vertical Settings-style Destination cards and separate detail pages instead
  of three unequal selector buttons.
- Show the positive Notification forwarding switch only on Home. A compact footer
  status navigates back to Home.
- Stop notification capture and new Outbox claims while Forwarding is disabled.
  Let already-started HTTP attempts finish, keep queued work durable, and do not
  backfill notifications that arrive while disabled.
- Give each configured Destination an independent enabled state. A disabled
  Destination retains its configuration and may still send an explicit test.
- Replace semicolon-oriented Filter text boxes with include/exclude keyword items.
- Make Activity describe actual send work, not every notification read during the
  current session.
- Present Generic Webhook as **Custom Webhook** / **自定义 Webhook** while retaining
  the technically precise internal type name and standard JSON payload contract.
- Discover Apps with an explicit one-time Notification Center snapshot that neither
  subscribes to changes nor creates Deliveries.
- Drive the Outbox by wake signals and the nearest retry deadline instead of a fixed
  five-second database poll.
- Do not show startup onboarding. Sign-in startup is an explicit Settings choice.

#### Execution order and contingencies

The checkpoint list is not the execution order. Work Slice 4 in this sequence:

1. **Verify the toolkit.** Query NuGet for a `CommunityToolkit.WinUI.Controls.*`
   release compatible with Windows App SDK 2.4.0 before writing any markup that
   depends on it.
2. **Build the token dictionary.** `Styles/AppStyles.xaml` is written but uncompiled.
   Run `dotnet build NotiRelay.slnx` and confirm the resource elements
   (`x:Double`, `Thickness`, `CornerRadius`) parse before building anything on them.
3. **Establish a verification surface.** It was later superseded by the shipping-page
   matrix because real content density and reflow must be reviewed in context.
4. **Rebuild the shell.** `Tall` title bar, pane toggle relocation, selection
   treatment, icon font.
5. **Migrate pages one at a time**, in this order: Settings, Rules, Destinations,
   Apps, Activity, Home. Settings and Rules are the smallest and exercise the
   group card and the chip flow respectively; Home is last because it depends on
   summary data whose shape the other pages settle.

**Keep the tree buildable at every checkpoint.** A page is migrated completely or not
at all; a superseded style is removed only after its last consumer is gone.

**Contingency if no compatible toolkit release exists.** Do not block. Build a
first-party `GroupCard` and row on top of the token dictionary, and use restyled
`RadioButtons` where the specification calls for `Segmented`. This is more work than
adopting the toolkit but still a large improvement over `SettingsRow`, and it keeps
ADR 0011 intact — the ADR commits to an owned content design system, not to a
specific package. Record the outcome in this milestone before proceeding.

### Slice 5 — Interface System Correction

The Slice 4 review failed for two independent reasons. The interface crashes the
process on navigation, so nothing in it has been validated at runtime. And the design
system it implemented specified *metrics* — type ramp, 4 px grid, radii, row heights,
breakpoints — without ever deciding **surface layering, colour usage, and information
density**, which is what actually separates the reference products from this one. It
also adopted the Windows Community Toolkit without overriding the toolkit's own metric
resources, so toolkit pages (Destinations, Rules, Settings) and hand-written pages
(Apps, Activity) render two visibly different card grammars — the exact defect Slice 4
existed to remove.

`docs/design/ui-system.md` has been rewritten with every decision below. Read it first;
this section is the execution plan, not the specification.

It supersedes these Slice 4 decisions:

| Superseded | Replaced by |
| --- | --- |
| Card title 18 px | 16 px, on the WinUI ramp, no line-height override |
| Page title plus a 14 px subtitle | Page title only; subtitles deleted everywhere |
| `MaxContentWidth` 1000, left aligned | **1200, centered, with 16/24/32 adaptive gutters** |
| Navigation selection = accent icon + SemiBold label | Native NavigationView selection, untouched; the code that attempted this is deleted |
| Forwarding footer item is a real toggle | Footer is a status row only; it navigates to Home |
| Notification-area forwarding entry is a read-only label | A checkable item — the second of only two control points |
| Display language as `Segmented` | `ComboBox`; `Segmented` is only for list filters |
| Toolkit adopted at its default metrics | Toolkit metric resources overridden onto the token dictionary |
| Destinations: three always-expanded cards | Configured and healthy cards collapse; unconfigured or failing expand |
| Closing the window always hides to the notification area | User-chosen Close Action ([ADR 0012](../adr/0012-let-the-user-choose-what-closing-the-window-does.md)) |
| Cards on Apps and Activity carry a card header | Single-card pages move summary and actions to the page title row |

1. **The tree has never been compiled since the last edits.** `dotnet build` was
   unavailable in the session that produced them (the shell returned exit code 2 for
   every command, including `echo`). These edits are unverified: `Styles/AppStyles.xaml`
   (`NavigationGlyphSize`, `TitleBarIconButtonStyle`, `ChipRemoveButtonStyle`),

3. **The toolkit's metric resource keys are unknown.** `ui-system.md` §14 records where
   to read them and what to map them onto. The installed package ships compiled XBF
   inside `.pri`, so they cannot be read from the NuGet cache.

#### Slice 5A — responsive settings experience

The first human review of Slice 5 accepted the Shell direction but found that the
fixed 760 px page column, breakpoint padding changes, and several provisional controls
did not behave like Windows Settings. Slice 5A applies these accepted decisions:

- The page column is centred and may grow to 1200 px. Content-width tiers use 16, 24,
  and 32 px outer gutters; card internal padding remains stable. A safe inset keeps
  overlaid scrollbars away from content. Accessory controls reflow at about 720 px of
  card width, not at a window-width breakpoint.
- The default effective window is 1040 x 720 and the minimum is 820 x 600. The
  persisted 232/48 navigation pane remains manually controlled and is not responsive.
- `主页` / `Home` is the only visible name for the first page.
- Apps uses a stable incremental filtered collection so switching All/Enabled does not
  recreate every toggle. Its summary is the total discovered count plus enabled count.
- Destinations use bounded readable fields, a persistent secret reveal button that
  resets when the page is left, and configured-state-driven expansion. Clearing is a
  distinct `Clear configuration` action.
- Rules uses two non-collapsible cards with independently persisted Include and Exclude
  enable switches. Keywords persist immediately; duplicates are case-insensitive;
  disabling a group preserves but ignores its chips; Exclude wins.
- Settings uses non-collapsible Startup and close, System, and Privacy and data sections.
  Silent Start is independent from Start at sign-in. Close Action is a ComboBox with
  Minimize to system tray, Exit, and Ask every time; the ask dialog can remember either
  completed choice. Display language is a ComboBox.
- Activity event grouping and filtering are deferred to Slice 5B. About, GitHub, and
  License UI are also deferred; no placeholder About surface is shipped in Slice 5A.

The second Slice 5A human review accepted a final Windows Settings-style correction:

- Content-width tiers are Compact `< 760`, Standard `760–1039`, and Wide `>= 1040`.
  Their horizontal gutters are 24, 40, and 56; top padding remains 24 and bottom
  padding remains 32 at every width so page titles do not move vertically.
- Group cards own no global content padding. Headers, setting rows, list rows, form
  rows, and action footers own their 24 px content inset; dividers are full width.
- Transient success and failure UI no longer inserts `InfoBar` rows. The owning action
  row or footer reserves a fixed status slot; field validation stays beside the field.
- Keyword chips are 8 px rounded rectangles rather than pills.
- Destination fields share one aligned control column and secrets use native Password
  Peek. The footer places status on the left and equal-sized Save, Send test, and
  confirmed Clear configuration actions on the right.
- The separate debug component page is removed. Home, Apps, Destinations, Rules,
  Activity, and Settings form the shipping-page verification matrix.
- Forwarding prerequisites update immediately from the source model. A visually
  enabled App must never remain disabled in `RelayRuntime`; satisfying the prerequisites
  enables the Home switch but never starts forwarding without an explicit user action.

## Window and Navigation Contract

| User choice | Navigation | Content behavior |
| --- | --- | --- |
| Expanded | Fixed 232 px side-by-side pane | Content uses the remaining width and may reflow vertically |
| Collapsed | Fixed 48 px side-by-side icon rail | Localized tooltips preserve the hidden labels |

The NavigationView does not use width thresholds. Its expanded/collapsed state is a
persisted user preference, and page content may still reflow as its available width
changes.

The first default client target is 1040 x 720 effective pixels. Native AppWindow
bounds are physical pixels, so both the default and minimum sizes are scaled using
the current window DPI. The window enforces an 820 x 600 effective-pixel minimum via
`WM_GETMINMAXINFO`; restored bounds are clamped to the same minimum and the current
display work area.

x64 remains the fully runtime-validated target. x86 is built and receives a basic
compatibility smoke test on x64 Windows. ARM64 remains compilation-only until it is
validated on physical hardware.
