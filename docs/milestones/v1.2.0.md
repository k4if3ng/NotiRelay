# v1.2.0 — Product Readiness and Supportability

## Status

Planned. v1.1.0 is complete; v1.2.0 is the next active product milestone.

## Objective

Make the existing notification-forwarding product easier to identify, inspect,
support, and publish without changing its provider-neutral capture, filtering,
routing, or at-least-once Delivery semantics.

v1.2.0 is a backward-compatible minor release. It adds user-observable capability
and compatible local schema changes, so it is not a v1.1 patch. Existing settings,
credentials, and durable Outbox Items must migrate without user intervention.

## Product and release boundary

- Windows 11 build 22621 or later.
- Packaged WinUI 3 MSIX with one Store-managed product identity.
- Microsoft Store is the only official binary-distribution, production-signing,
  and update channel.
- GitHub hosts source code, documentation, issues, pull requests, and tags; it
  does not host NotiRelay release binaries.
- x64 remains the primary runtime-validation and Store-submission architecture.
  x86 receives compatibility validation on x64 Windows. ARM64 remains
  compilation-only until physical-device or Store-flight evidence exists.
- Product version `1.2.0`, annotated tag `v1.2.0`, and MSIX package version
  `1.2.0.0` identify the same release. The MSIX Revision remains zero in
  repository builds.
- Author display is `凯风（Kaifeng）`; GitHub identity is `@k4if3ng`; the
  repository uses the MIT License with `Kaifeng` as the copyright holder.
- The release adds local diagnostics but no application telemetry, advertising,
  cloud account, or automatic diagnostic upload.

## Slice 1 — Repository governance and continuous integration

### Scope

- Protect `main` as the always-releasable integration branch.
- Require short-lived branches and pull requests for every Development Slice.
- Enable Squash Merge as the normal merge method and preserve one cohesive commit
  per slice on `main`.
- Add required Windows build/status checks before enabling the corresponding
  branch-protection requirement.
- Use Conventional Commit pull-request titles and automatically delete merged
  branches.
- Document the complete MAJOR, MINOR, PATCH, MSIX, tag, hotfix, and immutable
  artifact rules in `docs/development-workflow.md`.

### Acceptance

- Direct ordinary commits, force-pushes, and branch deletion are blocked on
  `main`.
- A sample pull request demonstrates the required checks and Squash Merge result.
- The repository remains usable by one maintainer with zero required approvals.
- A patch release can be produced from the latest supported tag without relying
  on a permanent `develop` branch.

## Slice 2 — Activity readability and privacy-bounded previews

### Scope

- Remove competing page and list vertical scroll regions; the page-level scroll
  host is the single vertical scroll owner.
- Add a separately derived Activity Preview: notification title first, otherwise
  a bounded body excerpt.
- Keep full title, body, and raw notification content out of terminal Delivery
  records.
- Add a compatible database migration for the preview field.
- Add a Privacy setting that enables or disables future preview retention;
  default enabled.
- Display at most two preview lines with trimming, wrapping, accessible semantics,
  and no width expansion.
- Keep preview retention bounded by the existing Activity cleanup policy and
  remove it through the existing clear-records action.

### Acceptance

- Small windows, mouse wheel, touchpad, keyboard scrolling, and 200% text scaling
  expose one predictable vertical scroll path.
- Existing databases migrate without losing configuration, credentials, or
  non-terminal Delivery work.
- Terminal records contain no full notification title/body, while enabled
  previews make recent records distinguishable.
- Disabling previews, after explicit confirmation, clears retained previews and
  prevents new preview retention without deleting other Activity metadata.
- Migration may derive previews only from content that is still present in
  non-terminal Deliveries; it never reconstructs past terminal content.
- Diagnostic logs and exported diagnostics contain no Activity Preview.

## Slice 3 — Home delivery-health semantics

### Scope

- Separate configuration counts from delivery-health metrics.
- Show enabled Apps and enabled Destinations as configuration state.
- Rename the current aggregate Pending count to `In queue` / `队列中`; it
  includes Pending, Active, and Retry Scheduled non-terminal work.
- Show explicit rolling `Sent (24h)` / `24 小时内成功` and `Failed (24h)` /
  `24 小时内失败` metrics.
- Record a terminal timestamp so the 24-hour window reflects completion rather
  than enqueue time; do not estimate historical completion times during migration.
- Keep Active and Retry Scheduled as Activity-level detail rather than separate
  Home counters.
- Preserve the forwarding precondition and do not enable Forwarding
  automatically when prerequisites become valid.

### Acceptance

- Every visible count has an explicit status set and time window.
- The counts update after enqueue, claim, retry, success, failure, cleanup, and
  restart.
- Compact, standard, and wide layouts remain readable without hiding operational
  meaning.
- Home continues to show only the three most recent sends beneath the summary.

## Slice 4 — Local diagnostics and support export

### Scope

- Replace scattered file appends and debugger-only messages with a bounded local
  diagnostic service.
- Record UTC time, level, event ID, category, operation correlation, application
  version, architecture, and sanitized exception information.
- Keep Activity Records and Diagnostic Logs as separate models and stores.
- Rotate logs by size and age; initial limits are 5 MiB per file, 10 files, and
  seven days.
- Cover startup, unhandled UI, navigation, forwarding state, background
  dispatcher, destination delivery, Activity refresh, and logging failures.
- Add a user-initiated sanitized diagnostic export from Privacy settings.
- Exclude notification content, Activity Previews, credentials, complete
  destination endpoints, databases, and Credential Locker data.

### Acceptance

- Representative failures retain the original exception category and correlation
  without leaking protected content.
- Logging failures do not crash or recursively log.
- Rotation enforces its limits across restart.
- No diagnostic data leaves the device automatically.
- The exported bundle can be inspected before the user chooses to attach it to an
  Issue.

## Slice 5 — Product identity, icons, and About

### Scope

- Preserve the existing NotiRelay application, package, window, and notification-
  area brand assets.
- Resolve and cache real Source Application icons locally, with a deterministic
  generic fallback and cache invalidation.
- Give Bark and Telegram reviewed destination identities; keep Custom Webhook on
  an application-owned semantic icon. Record asset provenance and brand usage.
- Add a Settings About group for installed version, author
  `凯风（Kaifeng）`, GitHub `@k4if3ng`, repository, Star, Issues, and MIT
  License.
- Read the installed product version from package or assembly metadata.
- Open external links with normal Windows launcher behavior and expose link
  semantics to accessibility tools.

### Acceptance

- Source icon extraction failure, uninstall, package update, light/dark/high-
  contrast themes, and 200% text scaling have reviewed behavior.
- No icon image BLOB enters the Source Application domain model or operational
  database.
- Destination artwork has documented provenance and permission.
- About metadata agrees with LICENSE, repository URLs, and product version.
- No version string is hard-coded in page XAML or localization resources.

## Slice 6 — Microsoft Store publication

### Scope

- Reserve/confirm the product in Partner Center and associate the project with
  the Store-managed Identity and Publisher.
- Finalize Store icon assets, listing copy, screenshots, support contact, and
  hosted privacy-policy URL.
- Produce the x64 upload package from final source and run Windows App
  Certification Kit.
- Submit a private package flight before public promotion.
- Validate installation, upgrade from the latest stable package and oldest
  supported baseline, notification permission, startup, tray lifecycle, durable
  retry, all Destination Types, and uninstall.
- Make the Store listing discoverable through WinGet's `msstore` source only if
  desired; do not publish an independent WinGet package.
- Update version surfaces, final validation evidence, release commit, and
  annotated `v1.2.0` tag through the protected-branch workflow.

### Acceptance

- The Store package carries the intended Store identity and trusted production
  signature.
- The installed About version is `1.2.0` and the package version maps to
  `1.2.0.0` before Store processing.
- Store install and supported upgrade paths preserve settings, credentials,
  preview preference, and non-terminal Outbox Items.
- GitHub contains no official MSIX, setup, or standalone EXE release asset.
- Public release claims do not exceed the architecture evidence actually
  collected.

## Explicitly deferred

- Source- or Filter-specific Route policies, multiple profiles of one Destination
  Type, and a visual Route editor. This remains the largest structural domain gap
  and is a candidate for a later minor milestone.
- Slack, Feishu/Lark, WeCom, and DingTalk.
- Full notification-content history and search.
- Cloud telemetry or automatic crash upload.
- Configuration import/export.
- Setup executables, unpackaged/single-file deployment, direct-download MSIX, and
  GitHub binary releases.
- Windows background-task hosting and runtime-loaded third-party adapters.
- Physical-device ARM64 claims without corresponding evidence.

## Validation matrix

- Debug and Release builds for applicable architectures.
- Resource parity and XAML localization coverage.
- Light, dark, and high-contrast themes.
- Compact, standard, and wide windows at 100% and 200% text scaling.
- Keyboard, pointer, touchpad, focus, tooltip, and screen-reader semantics.
- Existing-database migration and restart recovery.
- Privacy inspection of SQLite, diagnostic logs, and diagnostic exports.
- Microsoft Store private-flight installation and upgrade on Windows 11.

Validation evidence must follow `docs/development-workflow.md` and must not
contain notification content, Activity Previews, credentials, or personal data.
